# 01. 디자이너 시작하기 (바이브 코딩 워크플로우)

이 프로젝트는 **개발자가 뼈대를 만들고 디자이너가 그 위에서 AI 바이브 코딩으로 채우는** 구조다. 이 문서는 디자이너가 무엇을 어떻게 시작하는지, 개발자가 미리 만들어 주는 것이 무엇인지 정리한다.

---

## 1. 작업 분담 한눈에

```text
┌─────────────── 개발자가 미리 구축 ───────────────┐
│ · prefab(화면 구조) · 씬 · 레이어 트리            │
│ · @Serialize 배선(코드 ↔ prefab 노드 연결)        │
│ · 네트워크 · 서버 어댑터 · 로컬 목업              │
│ · 상태 관리 · 베팅 흐름 · 빌드 환경               │
│ · 색/타이포/좌표를 담는 prefab marker 자리        │
└──────────────────────────────────────────────────┘
                     │  (여기까지 완성된 상태에서)
                     ▼
┌─────────────── 디자이너가 바이브 코딩 ───────────┐
│ · 색 값 · 폰트 크기 · 레이아웃 값 조정            │
│ · 배경/아이콘/버튼 이미지 교체                    │
│ · 연출(이펙트) 강도·타이밍                        │
│ · 사운드 연결·볼륨·타이밍                         │
│ · 문구·라벨 · 슬라이더 범위 등 표시 값            │
└──────────────────────────────────────────────────┘
```

> "무엇이 안전하고 무엇이 금지인지"의 정확한 경계는 `02_수정_경계_가이드.md` 를 반드시 본다.
> Massive Mines의 규칙·RTP·오토·화면 골격은 `Massive_Mines_GDD.md` 가 정본이다.

---

## 2. 개발자가 구축해 주는 것 (디자이너는 참고만)

디자이너가 직접 만들 필요는 없지만, **이해하고 있어야 실수를 안 한다.** 자세한 내용은 `13_부록_개발자_구축영역.md`.

| 구축물 | 뜻 | 디자이너가 알아야 할 점 |
| --- | --- | --- |
| **prefab / 씬** | 화면의 구조(어떤 패널·버튼·텍스트가 어디에 있는지) | 노드 **이름**을 바꾸면 코드가 그 노드를 못 찾는다 → 이름은 그대로 둔다 |
| **@Serialize 배선** | prefab 노드를 코드에 연결한 선 | 노드를 지우거나 옮기면 배선이 끊긴다 |
| **네트워크 / 서버** | 결과를 서버가 정하고 클라는 연출만 함 | 확률·배당·payload 는 서버 계약값이라 임의로 못 바꾼다 |
| **디자인 토큰 marker** | 색·폰트 크기를 담아 두는 prefab 안의 특수 노드 | **색/폰트 값의 정본은 여기**다. 코드가 아니라 이 값을 바꾼다(또는 SceneMaker/개발자) |
| **빌드 환경** | vite/tsconfig/에셋 빌드 | 설정 파일은 건드리지 않는다 |

핵심 개념 한 줄: **"보이는 값(색·크기·폰트)의 정본은 prefab 이고, 코드는 그 값을 읽어서 그릴 뿐이다."**

## 4. 기본 워크플로우 (Figma MCP 기반)

```text
1. 개발자가 구축한 프로젝트를 연다 (prefab·환경 완성 상태).
2. Figma에서 목표 UI를 확정한다 (디자인 기준 = Source of Truth).
3. npm run dev 로 실행해 현재 화면을 확인한다.
4. 바꿀 대상을 정한다 (예: BET 버튼 색, 결과 연출 강도, 코인 아이콘).
5. 그 대상이 "안전 / 확인 필요 / 금지" 중 무엇인지 02 문서로 판단한다.
   - 안전이면 진행, 확인 필요면 개발자에게 문의, 금지면 하지 않는다.
6. Figma에서 대상 노드를 선택(select)하고, AI에게
   ① MD 가이드 ② 현재 prefab/코드 구조 ③ Figma 디자인 을 함께 기준으로 준다.
7. AI가 Figma MCP로 Figma 구조를 읽어 UI를 구현한다.
   (색·폰트·좌표는 코드가 아니라 prefab marker 에 적용)
8. 게임을 실행해 Figma ↔ Game Preview 를 비교하고, 08 연출 규칙(가림·강도)을 검수한다.
9. 차이가 있으면 6~8 을 반복한다.
10. 바꾼 것 / Figma 비교 결과 / 개발자 확인 필요 항목을 기록한다.
```

> Figma MCP 기반 제작 Workflow 전체 개요는 `디자이너_제작_가이드.md` 를 본다.

## 5. 절대 규칙 (디자이너 기준)

1. **prefab 노드 이름을 바꾸지 않는다.** 코드가 이름/배선으로 노드를 찾는다.
2. **색·폰트 크기·좌표를 코드에 하드코딩하지 않는다.** 정본은 prefab marker. 값 변경은 marker(또는 SceneMaker/개발자)로.
3. **원본 이미지는 `raw-assets/` 에서 작업**한다. `public/assets/` 는 빌드 결과라 직접 건드리지 않는다(→ `10`).
4. **확률·배당·payload·베팅 한도**는 서버 계약값이므로 임의로 만들지 않는다. 모르면 `확인 필요`.
5. **연출은 CTA·결과 금액·핵심 오브젝트를 가리지 않는다.**(→ `08` GROK 규칙)
6. `pixibrown/`, `src/common/`, `src/network/`, 빌드 설정은 **건드리지 않는다.**
7. 애매하면 임의로 정하지 말고 **개발자 확인 필요 항목**으로 남긴다.

## 7. 자주 하는 질문

- **"색을 바꾸고 싶은데 코드 어디를 고치나요?"** → 코드가 아니라 prefab 의 `PaletteMarkers` 값(또는 SceneMaker/개발자)을 바꾼다. (→ `04`, `10`)
- **"버튼 이미지를 교체하고 싶어요."** → `raw-assets/game/images/` 에 넣고 에셋 빌드 후 사용한다. (→ `10`)
- **"연출을 더 화려하게 하고 싶어요."** → 강도 표(1~10)와 가림 규칙 안에서 올린다. CTA·금액을 가리면 실패. (→ `08`)
- **"노드를 하나 지우면 안 되나요?"** → 지우면 배선이 끊긴다. 개발자 확인 필요. (→ `02`)
